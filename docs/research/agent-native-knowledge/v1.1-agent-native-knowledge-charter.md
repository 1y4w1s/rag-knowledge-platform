## 0. Executive Summary

v1.0 established that Suoyin can **measure** evidence-driven agent behavior (FactGoal, EvidenceLedger, Stop Policy, Critic, local GLM harness) without default rollout. v1.1 asks a different question:

> **Given the same agent control plane, corpus, and local model, which knowledge substrate best supports grounded, multi-hop, explainable answers — and at what cost?**

This charter is an **executable research engineering program**, not a technology trend survey. Every substrate claim must pass: fixed controls, frozen benchmark matrix, denominator, baseline, cost accounting, failure taxonomy, and scope limitation.

**Non-goals for v1.1 P0**: default rollout, MCP breadth, Multi-Agent orchestration, self-evolving KB writes at runtime, production GraphRAG enablement, or modification of v1.0 golden fixtures.

## 1. Core Research Question

Under the **same** Agent loop, FactGoal decomposition, EvidenceLedger integration, Stop Policy, Critic, and local small model (`zai-org/glm-4.6v-flash` or successor freeze profile):

**Which knowledge substrate maximizes grounded task success per unit cost?**

### 1.1 Knowledge Substrates Under Comparison

| ID | Substrate | Description | v1.1 P0 |
|----|-----------|-------------|---------|
| **A** | Flat Vector / Hybrid RAG | Current production path: PostgreSQL FTS + pgvector + RRF (`w_v=1.0 / w_f=1.5`); chunk-level index | **Baseline** |
| **B** | Fact-Decomposed Hybrid RAG | Substrate A + L4 FactGoal-driven retrieval planning (missing-fact targeted re-retrieval) | **P0** |
| **C** | Graph-based retrieval | Entity/relation index + graph walk recall (GraphRAG / LightRAG class; **implementation TBD — P0 audit gate**) | **Optional baseline** |
| **D** | LLM-Wiki / compiled knowledge | Offline compilation of corpus → structured wiki pages / fact cards / Q→A pairs | **P0 design + pilot** |
| **E** | Wiki + Hybrid | Compiled wiki as first-pass lookup; hybrid RAG as fallback / verification | **P0** |
| **F** | Self-evolving knowledge | Agent failure → Error Book → repair proposal → offline validation → versioned KB update | **Design only (v1.2)** |

### 1.2 Trade-off Dimensions (All Required in Reports)

| Dimension | Definition |
|-----------|------------|
| **Accuracy** | Task success vs frozen answer key (acceptable-set where applicable) |
| **Evidence quality** | Precision/recall of EvidenceItem ↔ FactGoal edges |
| **Multi-hop** | Completion rate on B2 / graph-traversal queries |
| **Cost** | Index/build wall time, incremental update cost, query tokens, generation tokens |
| **Latency** | P50/P95 end-to-end and per retrieval hop |
| **Explainability** | Citation correctness, provenance traceability, human-auditable hop log |
| **Local-model stability** | Planner parse validity, timeout rate, safe outcome rate under fixed timeout (90s) |

**Research discipline**: Feature implemented ≠ useful. Claims require denominator, baseline, cost, failure cases, and explicit scope limitation.

### 2.5 Answer: What Can Be Fixed Control Plane?

**YES** — the following are suitable **fixed controls** for knowledge-substrate experiments:

1. **FactGoal lifecycle** — decompose → match → ledger → stop (W1–W5, wired, default OFF)
2. **EvidenceLedger semantics** — all substrates must emit `EvidenceItem` edges, never Wiki-only truth
3. **Stop Policy** — same budget, same conflict/missing rules
4. **Critic** — same claim-check pipeline before publish
5. **Planner + tool schema** — same action space; only knowledge tool backends swap
6. **Local model + harness** — same model profile, timeout, scoring rubric
7. **Corpus + kb_id isolation** — same frozen benchmark corpus per matrix cell

**NOT fixed (substrate variables)**: index structure, compilation pipeline, retrieval API implementation, hop strategy, precompute vs query-time compute.

## 3. Four-Layer Architecture

v1.1 organizes work into four layers. Layers 2–4 are **control-plane extensions**; Layer 1 is **substrate-variable**.

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 4: Evaluation Layer                                   │
│   Fixed agent · fixed evaluator · fixed model · swappable   │
│   substrate adapter · frozen benchmark matrix A–F           │
├─────────────────────────────────────────────────────────────┤
│ Layer 3: Evidence Integration                               │
│   All substrates → EvidenceItem → FactGoal → EvidenceState  │
│   No Wiki-only truth · provenance required                  │
├─────────────────────────────────────────────────────────────┤
│ Layer 2: Agent-Native Retrieval Interface                   │
│   knowledge_search · knowledge_read · knowledge_follow      │
│   knowledge_lookup · hybrid_search (graph optional)         │
├─────────────────────────────────────────────────────────────┤
│ Layer 1: Knowledge Compilation Layer                        │
│   Precompute vs query-time · compilation hallucination audit│
│   Substrate-specific indexes (vector / graph / wiki)        │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 Layer 1 — Knowledge Compilation Layer

**Research questions**: What should be precomputed vs resolved at query time? Where does compilation hallucinate?

| Substrate | Compilation artifact | Build trigger | Hallucination audit |
|-----------|-------------------|---------------|---------------------|
| A/B | Chunk embeddings + FTS | Ingest pipeline | N/A (no generative compile) |
| C | Entity/relation graph | Offline extract + optional LLM summarize | Manual spot-check + auto consistency vs source chunks |
| D | Wiki pages / fact cards | Offline LLM compile job | **Mandatory** human-or-gold audit sample (≥10%) |
| E | Wiki + chunk index | Dual pipeline | Wiki audit + hybrid fallback log |
| F | Versioned patch sets | Failure-driven offline | Regression benchmark gate |

**Deliverable (K2)**: Compilation contract doc + hallucination audit protocol for D/E.

### 3.2 Layer 2 — Agent-Native Retrieval Interface

Agents must not see substrate internals. All substrates implement a **common tool surface**:

| Tool | Semantics | Substrate mapping |
|------|-----------|-------------------|
| `knowledge_search` | Broad recall by natural language query | A/B: hybrid; C: graph+hybrid; D/E: wiki search |
| `knowledge_read` | Fetch bounded excerpt by stable ID (chunk_id / wiki_page_id / node_id) | All |
| `knowledge_follow` | Traverse relation (C: edge; E: wiki link; A/B: doc/chunk adjacency if available) | C/E primary |
| `knowledge_lookup` | Exact key lookup (entity, policy ID, version) | C/D/E |
| `hybrid_search` | Explicit hybrid RAG path (baseline tool) | A/B/E fallback |

**Design rule**: Planner prompt and tool schema **unchanged** across matrix cells; only adapter backend swaps.

**Graph optional**: `knowledge_follow` may no-op with structured `unsupported` observation on substrates A/B/D.

### 3.3 Layer 3 — Evidence Integration

Every retrieval observation passes through:

```text
Tool result → snippet extraction → EvidenceMatcher → EvidenceItem[] → FactGoal status update → EvidenceState sync
```

**Hard invariants**:

- Wiki/compiling substrate answers **cannot** bypass ledger (no "trust the summary")
- Each `EvidenceItem` carries `provenance` (substrate, source_id, excerpt_hash)
- Conflicts surface as `FactStatus.conflicted` → Stop Policy refuse path
- Critic validates **published** answer against ledger + citations, not raw wiki text

### 3.4 Layer 4 — Evaluation Layer

Substrate swappable via config flag / harness injection. Fixed:

- Corpus snapshot ID
- Local model profile
- FactGoal labels (human or frozen decomposer output per case)
- Scoring rubric (see §6)
- Agent flags profile (documented per matrix cell — e.g. B enables decomposer)

## 5. Metrics (All Required)

Every matrix report must include **all** metrics below. Missing metric = incomplete run.

### 5.1 Quality

| Metric | Definition |
|--------|------------|
| Answer accuracy | Primary task success / frozen denominator |
| Evidence precision | Correct FactGoal edges / emitted edges |
| Evidence recall | Covered required facts / all required facts |
| Citation correctness | Valid chunk/wiki provenance in final answer |
| Unsupported claim rate | Critic-flagged or evaluator-failed claims / total claims |
| Multi-hop completion | B2-class success rate |
| Hop efficiency | Successful multi-hop / total retrieval steps |
| Conflict detection rate | Detected conflicts / injected conflict cases |
| Stop correctness | Appropriate finish/refuse/partial vs gold terminal class |

### 5.2 Cost & Performance

| Metric | Definition |
|--------|------------|
| Retrieval steps | Tool calls classified as knowledge retrieval |
| Context tokens | Prompt context window usage (per turn, total) |
| Prompt tokens | Planner + tool schema overhead |
| Generation tokens | Model output tokens |
| Index/build cost | Wall time + CPU/RAM to build substrate index |
| Incremental update cost | Per-document add/update for substrate |
| Query latency | P50/P95 per query |
| Index latency | Retrieval-only P50/P95 |
| Disk footprint | Index + compiled artifacts on disk |
| Peak RAM/VRAM | Peak during query batch |

### 5.3 Agent Stability (Local Model)

| Metric | Definition |
|--------|------------|
| Local-model timeout rate | Planner or tool timeouts / trials |
| Planner parse validity | Valid `AgentDecision` / total planner calls |
| Safe outcome rate | finish/refuse/clarify without unsafe accept |

## 6. Research Questions RQ1–RQ8

| ID | Question | Primary matrix cells | Success criterion |
|----|----------|---------------------|-------------------|
| **RQ1** | Does FactGoal decomposition (B) improve multi-hop accuracy enough to justify L4 flag cost vs flat hybrid (A)? | A vs B | Δ accuracy > 0 with p95 latency ≤ 1.5× A |
| **RQ2** | Can compiled LLM-Wiki (D) match hybrid evidence recall with fewer retrieval hops? | A vs D | Hop efficiency ↑ AND unsupported claim rate ≤ A |
| **RQ3** | Does Wiki+Hybrid (E) dominate D on conflict and low-recall cases without exceeding cost budget? | D vs E vs A | B6/B7 strata win rate ≥ 2/3 |
| **RQ4** | Does graph retrieval (C) add measurable gain on entity-relationship queries beyond B? | B vs C | Q11 stratum Δ ≥ 15% with audit-pass graph |
| **RQ5** | Are failures substrate-specific or control-plane-specific? | All | Failure taxonomy ≥ 80% classified |
| **RQ6** | What is the Pareto frontier of accuracy vs total tokens across substrates? | All | Frontier chart + knee point identified |
| **RQ7** | How stable is local GLM planning across substrates (parse validity, timeout)? | All | Timeout rate ≤ 10%; parse validity ≥ 90% |
| **RQ8** | Does compilation hallucination rate bound D/E accuracy ceiling? | D, E | Audit sample ≥ 10%; hallucination ↔ error correlation reported |

## 8. Self-Evolving Knowledge (Design Only — v1.2)

v1.1 **designs** but does **not implement** substrate F.

### 8.1 Closed-Loop (Offline Only)

```text
Agent failure (evaluator negative)
  → Failure taxonomy tag
  → Error Book entry (case ID, substrate, fact IDs, trace)
  → Repair proposal (human or LLM draft)
  → Offline validation on holdout set
  → Accepted update → versioned KB patch
  → Full regression benchmark (A–E)
  → Rollback pointer if regression
```

### 8.2 Hard Constraints

| Constraint | Rationale |
|------------|-----------|
| **Auditable** | Every patch has author, rationale, source evidence |
| **Reversible** | Version pin + rollback ≤ 1 command |
| **Versioned** | KB snapshot ID in every EvidenceItem provenance |
| **Evaluation-gated** | No patch without regression pass on frozen matrix |
| **No runtime self-modify** | Agent cannot write KB from one wrong answer |
